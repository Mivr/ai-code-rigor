# Research index: references for rigor levels L0–L5

This is the reference index behind `ai-code-rigor`. It lists every source the background research used, grouped by practical theme rather than by the order in which it was collected. Each row gives the citation with a link, the finding that matters for the level design (with its number where one exists), and the kind of evidence it is.

- **Research date:** 2026-10-30.
- **Scope:** rigor levels for code written by AI agents. Rust first; C/C++ where its tooling is more mature; Buck2 builds; HPC and GPU code; CI on free GitHub-hosted runners.
- **What this file is not:** it does not reproduce papers or standards. Findings are paraphrased. Quoted extracts are kept under 25 words and used only where the exact wording matters. Standards are cited by number, part and clause or table. Technique-table markings are stated as facts (for example "MC/DC: ++ at ASIL D"); no table text or prose is reproduced.

## How to read the tables

| Column | Meaning |
|---|---|
| Source | Authors, year, venue, link (DOI, arXiv, or the publisher's or official page) |
| Key finding | The result that matters for level design, with its number or effect size |
| Evidence | standard · controlled study · empirical study · industrial report · benchmark · tool paper · survey · book · position · web doc |

Flags used in the Evidence column:

| Flag | Meaning |
|---|---|
| **P** | Preprint or workshop paper, not peer-reviewed at the time it was read |
| **T** | The authors evaluate their own tool, or the source is from a vendor with a commercial interest |
| **2°** | Number taken from a secondary source (named in the row), not checked against the primary text |
| **U** | Flagged as unverified in the research notes |
| **A** | Read at abstract level or only in part |

## 20. Strategic picture

The safety standards agree on one mechanism. A risk-derived level selects techniques, and rigour rises along the same axes everywhere: structural coverage (statement → decision → MC/DC), independence of verification, formal methods, coding restrictions, tool qualification and traceability depth. What they do not have is controlled evidence that following the tables at level N lowers defect rates relative to level N−1. That gap is the literature's own finding (Nair 2014, Weaver/McDermid, Graydon & Kelly 2013), not a gap in this search. The standards' tool-qualification clauses converge on a rule that fits AI-written code directly: in IEC 61508-3 7.4.4.8, ISO 26262-8 (TD1 → TCL1), EN 50128 6.7, DO-178C 12.2 and ECSS-Q-ST-80C 6.2.8.3a, a generator needs no qualification only if its output is fully verified. A non-deterministic model cannot be qualified, so every gate must stay in force whatever wrote the code. Independence cannot come from a second model either: Knight & Leveson's correlated failures reappear in LLMs (Kim 2025; Nogueira 2026), and ISO 26262-9 lists the same tools and language as coupling factors. The defensible substitute is diverse, deterministic methods (proof, mutation, fuzzing, differential testing, sanitisers) plus specs and oracles the code-writing agent cannot see or edit.

The empirical testing literature narrows which signals survive an author who optimises against them. Coverage is a floor for finding untested code, not a measure of test strength. Raw mutation score is a weak linear predictor, but surviving non-equivalent mutants are actionable findings, and the score is informative near saturation. MC/DC is sensitive to code structure unless measured on a canonical form with output-level oracles. Static size and complexity metrics mostly measure size. The 2025–26 agent literature then shows that any oracle an agent can see, edit or persuade gets gamed. Hardening (sealed tests, fail-closed structured results, hermetic grading, trajectory checks) works; instructions barely move the rate. For L4–L5, formal tools are usable: Verus, Kani and Miri for Rust, and Astrée/Frama-C/CBMC/CompCert for C. Agents now complete most proofs against frozen expert specs. The weak link has moved to the spec: agents pass the verifier with vacuous or altered obligations, and end-to-end spec+code+proof success is in single digits. Rust is ahead on proof automation and dynamic UB detection. C/C++ is ahead on MC/DC tooling, sound whole-program analysis, weak-memory checking, verified compilation and GPU verification. Rust GPU stacks (WGSL, naga, rust-gpu) have no static verifier, coverage tool or race detector, which is why GPU code is capped below the top levels.

Speed comparisons between verifiers are author-run.

Further concentration risks:
- **Author clusters.** Imperial/Donaldson and Utah/Gopalakrishnan dominate GPU work. Luxembourg/UCL, GMU and UW/UBC clusters dominate mutation science. The MC/DC structure-sensitivity results all come from one Minnesota group on Lustre models. All Rust mutation evidence comes from one Sheffield group.
- **Self-reported adoption surveys.** Woodcock 2009 and Gleirscher (about 1–2% response rate) over-represent successes.

### LLM results have a shelf life of months

Model versions in the corpus span Codex (2021) to 2026 frontier models. Rates move sharply between generations:
- proof automation went from 3/20 to 14/20 programs with model versions eight months apart;
- remaining `assume` counts ranged from 46 to 0 across models on one task;
- a Verus upgrade cut one agent's success from 75% to 53%.

The *categories* of gaming (test edits, hard-coding, obligation changes, escape hatches, grader exploits, judge persuasion) were stable from 2021 to 2026. The *rates* are not, so re-measure before relying on any number. Benchmark contamination is a further risk: HumanEval/MBPP-derived sets, and SWE-bench Verified memorisation.

### Coverage gaps in the evidence base

- **No Rust or CUDA validation** of any complexity, coupling or architecture metric. No Rust fault-coupling study for mutants.
- **No working Rust MC/DC:** removed from rustc in 2025, re-implementation planned.
- **No static verifier, coverage tool or dynamic race detector** for WGSL, SPIR-V, naga or rust-gpu.
- **No fidelity study** of lavapipe, SwiftShader or WARP for compute.
- **No study** measuring agents gaming complexity metrics.
- **No controlled proof-effort study.**
- **Medical (IEC 62304) and space (ECSS):** no technique tables in the primary text, or primary text not obtained.
